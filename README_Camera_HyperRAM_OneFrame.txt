# One-frame GC0308 to HyperRAM capture

## Source files

- `camera_interface_one_frame.vhd`: the refined camera configuration and one-frame DVP capture block.
- `Camera_HyperRAM_OneFrame.vhd`: top-level integration, RGB565-to-RGB888 conversion, asynchronous FIFO, HyperRAM write, full readback, and CRC check.

Set the Gowin project top entity to `Camera_HyperRAM_OneFrame`.

## Existing project dependencies

These are still required and are not re-created by these two files:

- `i2c_master_nack`
- Gowin PLL IP `Gowin_PLLVR_1`: 8 MHz input to 24 MHz output
- Gowin PLL IP `Gowin_PLLVR`: 24 MHz input to 96 MHz output, including `lock`
- `HyperRAM_Memory_Interface_Top` generated by the Gowin HyperRAM IP

The camera block now takes the shared 24 MHz clock from the top module. This avoids the two original files declaring different interfaces for a component with the same `Gowin_PLLVR` name.

The HyperRAM IP is expected to provide the same 48 MHz user clock and 32-bit user interface used by the earlier burst test. The top module preserves the previous 8-beat burst schedule and address increment of 16. Its one-cycle FIFO prefetch is accounted for by shortening the write idle gap by one cycle so the normal command-to-command interval remains 21 user-clock cycles.

## Inputs

- `clk8`: board 8 MHz reference clock.
- `rst_n`: global active-low reset. This is not the capture command.
- `rst_trigger`: one rising-edge pulse from the UART. It starts camera configuration; after successful configuration the camera block waits for the next frame and captures one frame only.
- `cam_pclk`, `cam_vsync`, `cam_hsync`, `cam_pix_data`: GC0308 DVP interface.
- Camera I2C and HyperRAM pins connect to their corresponding physical pins.

`rst_n` and `rst_trigger` have different jobs. Do not connect the UART trigger to `rst_n`.

## Frame contract

The defaults are 640 x 480. The camera capture block assumes active-high VSYNC and HSYNC, matching the register profile in the supplied camera design.

It emits bytes only while an active line is present. A frame is accepted only if it contains exactly:

- 480 active lines
- 1280 active bytes per line (640 RGB565 pixels x 2 bytes)

A short line, long line, extra line, incomplete final line, or failed camera configuration raises `frame_error_o`. The controller will not report successful completion for a partial frame.

This exact-length check is intentional. Before relying on the 640 x 480 default, verify that the captured DVP timing really has 1280 valid bytes per active HSYNC and 480 active lines. The camera source's register comments describe a 640 x 480 valid image, but the physical DVP timing must still be confirmed on the board.

## Pixel memory format

The sensor is configured for RGB565. Two consecutive input bytes make one pixel:

- First byte: `R[4:0] & G[5:3]`
- Second byte: `G[2:0] & B[4:0]`

The top module expands each component to 8 bits by bit replication, then stores one 32-bit word per pixel:

`0x00RRGGBB`

Examples:

- RGB565 `F8 00` (red) -> `00 FF 00 00`
- RGB565 `07 E0` (green) -> `00 00 FF 00`
- RGB565 `00 1F` (blue) -> `00 00 00 FF`

The memory is row-major:

`pixel_word_index = y * 640 + x`

Every line occupies 640 words. Since 640 is divisible by eight, each line consists of exactly 80 HyperRAM bursts and no burst crosses a line boundary.

For the supplied burst-address convention, burst `b` starts at HyperRAM IP address `b * 16`. The line start for row `y` is burst `y * 80`, i.e. IP address `y * 1280`. The readback index output is the linear pixel word index, not the raw HyperRAM IP address.

## Operation

1. Release `rst_n`.
2. Wait for `init_calib_o = '1'` and for the camera's I2C power-on delay to finish.
3. Send one rising-edge pulse on `rst_trigger`.
4. The camera is configured and then captures one frame.
5. Pixel words pass through a 1024-word asynchronous FIFO into the HyperRAM user-clock domain.
6. The controller writes all 307,200 pixel words.
7. After writing, it reads all 307,200 words back.
8. It calculates the same MSB-first CRC-32 over the write stream and readback stream. `done_o` becomes high only when the counts are complete and the CRC values match.

The CRC is a strong transfer check, not a mathematical proof that every possible corruption is impossible.

## Readback interface

The readback stream is in the HyperRAM user-clock domain:

- `readback_clk_o`: clock for the stream.
- `readback_valid_o`: one-cycle valid pulse.
- `readback_data_o`: current 0x00RRGGBB pixel word.
- `readback_index_o`: linear pixel index, 0 through 307199.

For a given valid readback word:

- `x = readback_index_o mod 640`
- `y = readback_index_o / 640`

`read_count_o` reaches 307200 after all words are read. `read_crc_o` should equal `write_crc_o`.

## Useful GAO/ILA probes

Recommended first capture:

- `camera_config_done_o`, `camera_config_pass_o`
- `camera_line_count_o`, `camera_line_byte_count_o`
- `frame_done_o`, `frame_error_o`
- `fifo_level_o`
- `state_dbg_o`
- internal `cmd_i`, `cmd_en_i`, `addr_i`, `wr_data_i`
- internal `rd_data_i`, `rd_data_valid_i`
- `write_count_o`, `read_count_o`
- `write_crc_o`, `read_crc_o`
- `done_o`, `error_o`

Expected end state for 640 x 480:

- `write_count_o = 307200`
- `read_count_o = 307200`
- `write_done_o = '1'`
- `read_done_o = '1'`
- `done_o = '1'`
- `error_o = '0'`
- `write_crc_o = read_crc_o`

## Important verification note

These VHDL files were assembled from the supplied source and reviewed for integration consistency, but they were not compiled or timing-verified with Gowin EDA in this environment. In particular, confirm the HyperRAM IP's generated user-clock frequency, burst data-valid timing, and dual-clock FIFO RAM inference in Gowin synthesis before relying on a full-frame run.
