# GC0308 -> HyperRAM Capture Migration Log

## Scope and invariant

This branch is intended to replace the synthetic byte source in
`HyperRAM_Storage_SelfTest` with the real GC0308 DVP stream.

The primary invariant is that the interface of
`rgb565_frame_packer` and every block after it remain unchanged unless a
clock-domain or CDC requirement makes a narrowly scoped change necessary.

The packer contract is:
- `cam_byte_i[7:0]`: one RGB565 byte, MSB first within each pixel.
- `cam_byte_valid_i`: one-cycle pulse in the same clock domain as
  `cam_pclk`.
- `cam_frame_done_i`: one-cycle end-of-frame event in that same domain.
- `cam_frame_error_i`: frame/source error in that same domain.
- Four valid bytes form one 32-bit word in byte order
  `byte0 & byte1 & byte2 & byte3`.

## Existing camera block findings

`camera_interface.vhd` already implements both:
1. GC0308 register configuration over SCCB/I2C, including a readback check
   that register page 0, address 0x24 contains 0xA6 (RGB565).
2. DVP capture using `cam_pclk`, `cam_vsync`, `cam_hsync`, and
   `cam_pix_data[7:0]`.

Its stream output is a byte stream, not a 16-bit pixel bus. This is the
correct shape for the existing packer; no RGB565-to-byte adapter should be
inserted between this module and the packer.

The camera block's output stream is in the `cam_pclk` clock domain.
Therefore:
- The packer clock must be `cam_pclk`.
- The write clock of capture FIFO #1 must also be `cam_pclk`.
- The read side of capture FIFO #1 remains in `usr_clk`.
- FIFO #1 is the intended CDC boundary between camera capture and the
  HyperRAM user-clock domain.

This is a necessary clock-domain correction. Keeping the FIFO write clock
at `clk24` while feeding it data/valid generated by `cam_pclk` would be
an unsafe asynchronous crossing.

## Intended top-level source control

The source-control sequence is to be explicit and observable:

1. `SOURCE_IDLE`: wait for the existing capture/transfer trigger.
2. `CAMERA_CONFIG`: issue a one-cycle start pulse to the camera block and
   wait for `config_done`.
3. On `config_pass=1`, transition to `CAMERA_READ`.
4. On `config_pass=0`, latch a source/configuration error and do not start
   storage capture.
5. `CAMERA_READ`: accept the camera byte stream until frame_done or error.

The camera interface itself contains a configuration FSM and a DVP capture
FSM. The top-level source FSM must not fight those internal state machines;
it supervises the configuration result and exposes the requested
CONFIG -> READ sequence to the rest of the system.

## Downstream preservation

The following are preservation targets:
- `rgb565_frame_packer.vhd`: no functional edits intended.
- FIFO #1 read-side interface and HyperRAM writer FSM: no functional edits
  intended.
- HyperRAM IP interface, burst schedule, readback, serializer, UART framing:
  no functional edits intended.

Required CDC-related updates may include the FIFO write clock and any
capture-domain status/snapshot synchronizers. Such changes must be justified
and logged separately.

## Build integration still to complete

The synthetic self-test project currently lists the generator but does not
list `camera_interface.vhd` or `i2c_master_nack.vhd`. The project file must
be updated when the real camera source is integrated.

The self-test top-level currently has no GC0308 physical ports. Camera DVP,
SCCB pins, and the sensor clock output must be added and mapped using the
verified Tang Nano 4K camera connector pinout. Pin assignments must not be
guessed.
